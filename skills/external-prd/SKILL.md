# 对外 PRD 文档

制作客户能理解、评审者能核对、实施人员能据以执行的产品需求文档。采用朴素、正式的中文商务排版，以业务流程串联功能，使用统一的多级标题、表格与图注。

## 制作流程

1. 阅读用户提供的需求、已有文档、系统资料及已确认结论，确定文档名称、读者、版本和本次交付内容。已有信息充分时直接推进；影响业务结论的缺口整理为具体待确认项。
2. 阅读 [内容结构](references/content-structure.md)，以“项目理解 → 业务流程 → 功能需求 → 实施与保障”组织内容。按项目规模调整章节深度。
3. 为功能分配稳定需求编号，先整理功能总表，再展开重点功能。将已确认规则、建议规则、待确认事项清楚区分，按资料中的证据描述现有能力。
4. 阅读 [排版规范](references/document-style.md)，使用命名样式建立正文、三级标题、表格、图注、目录、页眉页脚。有用户指定样式时遵循用户要求。
5. 需要起稿时参考 [PRD 大纲](assets/prd-outline.md)，替换示例章节和填写提示，写成完整的项目正文。
6. 制作可编辑 DOCX。环境提供文档制作工具或 skill 时使用其能力；否则采用支持 Word 标题样式、编号、字段和分页的文档库。章节使用真实标题样式，目录使用自动目录字段。
7. 按 [交付检查](references/delivery-checklist.md) 核对内容和排版。渲染后逐页检查，更新目录和交叉引用；若当前工具无法更新字段或渲染，准确说明尚未验证的部分。

## 写作方式

- 以客户业务语言说明功能，再给出规则、管理方式和验收结果。
- 每个核心功能写清：谁使用、何时触发、操作步骤、处理规则、结果、异常和权限。
- 前台操作与后台管理互相对应，涉及外部系统时说明交换数据、触发时机和失败处理。
- 将已有能力、项目适配和拟建设需求分别表述。功能菜单或截图可以证明入口存在，完整流程的结论需要相应验证依据。
- 参数、期限和指标有来源才写为确定值；建议值标明“建议”，未定项列明确认内容及影响。
- 用具体行为替代宣传性词语，例如“审核通过后记录审核人和时间，申请人可查看结果”。

## 默认效果

白底、仿宋、黑色正文；三级章节编号；浅灰表头和细边框；自动目录；简洁页眉页脚。通过字号、字重、间距和图表层次组织阅读。
